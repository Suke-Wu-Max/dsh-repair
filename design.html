dsh-tudian DSH 启动失败修复工具 · 架构设计

目标：让任何一个遇到 DSH 起不来的用户，敲一条命令就能修好 —— 不用知道任何路径、端口、内部机制。

零第三方依赖 Windows / macOS / Linux Node ≥ 18 可运行 全中文 幂等 · 可回退

一、一条命令，五个阶段

npx dsh-tudian —— 用户只需要记住这一句。

① 探测环境体检
全部只读
② 诊断判定故障类型
纯判断
③ 修复真正动手
唯一会写盘
④ 验证端口 + HTTP
双重确认
⑤ 报告中文报告
+ 日志留痕
关键设计：三层严格分离。 探测层只读 → 诊断层只判断 → 修复层才写盘。
所以 --dry-run（只检测不修复）的安全性是一眼可查的： 想确认它有没有偷偷改东西，只需要 grep 一个文件 lib/repair.mjs。

二、分层与文件

层文件职责会写盘吗
入口bin/dsh-tudian.mjs参数解析、帮助、退出码否
基础lib/exec.mjs跨平台命令执行（三个平台坑都在这）否
lib/log.mjs日志（写不进来自动降级，绝不影响主流程）日志文件
lib/ui.mjs中文输出、进度、确认交互否
lib/util.mjs纯函数（版本比较、链接识别、路径缩写）否
lib/net.mjs端口与 HTTP 探测（只用 net 模块）否
lib/registry.mjs软件源探测与切换（温和档优先）仅加 --persist-registry 时
探测层lib/probe.mjs系统 / Node / npm / DSH / profile / 端口 / 配置 / 备份否
诊断层lib/diagnose.mjs七类故障判定 + 启动日志解析否
修复层lib/repair.mjs备份 / 恢复 / 建链接 / 装包 / 启动 / 验证是
编排层lib/flow.mjs把上面串成一条线 + 分派修复路径间接
报告层lib/report.mjs打印中文报告与后续建议否

三、故障诊断表

诊断返回 主因 + 次因，不是一个菜市场清单 —— 因为 Node 版本太低的时候，后面那些"插件没装、端口没起来"全是后果，跑去修它们是浪费时间还可能改坏好配置。

故障判据自动修怎么做
Node 版本过低版本 < 22.19.0否给升级步骤（工具自身能在 18 上跑，就为了还能说这句话）
npm 没装PATH 里找不到 npm否提示去装 Node.js
npm 跑不起来命令在，执行失败否继续修别的 —— 恢复备份/建链接/启服务都不需要 npm
找不到 DSH 本体六路探测全落空否提示用 --home 指定
没有可用 profileprofiles 目录下没有 profile否给出从模板新建的命令
profile 目录没写权限目录不可写否给改权限的具体命令
配置文件损坏Tab 缩进 / 顶层非数组 / 引号不闭合是从历史备份恢复（恢复前双重备份）
插件加载失败登记的插件在 node_modules 里解析不到是见下方四级降级
端口被占用打算用的那个端口上不是 DSH是换空闲端口启动
服务未启动端口没监听，配置正常是直接启动并等端口就绪
未知静态检查都过，启动仍失败否老实说不确定，把真实报错摆给用户

四、插件故障：刻意排好的四级降级

✗ 绝不能一上来就"禁用全部插件" —— 那是拿用户的一整套插件去赌一个问题插件。
级别动作代价何时才用
①重建 node_modules 链接插件功能完整保留首选。实测本机就是这个状态：plugins/dsh-say/ 目录好好的，只是少了一条链接
②重新安装插件功能保留，需联网本地没源码时；用临时源，不动全局 npm 配置
③停用那一个插件只损失这一个前两步修不好；用 DSH 原生 disabled 补丁，原内容零改动
④安全模式（全部停用）所有用户插件失效最后手段。默认不执行，要用户点头（回车＝不动手），随时 dsh-fix clear 撤销

五、安全设计

规矩怎么落实
改文件前先备份命名 xxx.bak-<时间戳>，跟 DSH 自己的一致；备份失败就中止整个流程
备份要幂等备份前算 SHA-256 指纹，内容相同就复用 ⇒ 连跑十次也只有一份备份
只做加法不做减法停用插件＝追加一条 disabled 补丁，原内容一个字节都不动
不删用户数据"清缓存"用的是 npm cache verify（只清损坏条目），不是 cache clean --force
不改用户配置装包只给单条命令加 --registry；改全局源需显式 --persist-registry，且记录原值
不误删真目录建链接时若发现同名真实目录，直接放弃并告诉用户，绝不删除
危险操作先问总确认 + 恢复备份单独确认 + 安全模式默认否；非交互终端下默认不执行修改

六、三条来自真实踩坑的设计决定

① 端口探测只能用 Node 的 net 模块，不能用 netstat / Get-NetTCPConnection。
实测：DSH 明明在 3080 上跑着，Get-NetTCPConnection -LocalPort 3080 -State Listen 却返回空， 于是判断成"端口空闲、服务没起来"—— 完全反了。
这类"系统工具被权限限制后静默返回空结果"的坑很阴险：它不报错，只是悄悄少给你东西， 然后你就把那个空结果当结论了。net.connect() 不受这类限制，跨平台行为也一致。
② Windows 上永远走 npm.cmd，绝不碰 npm.ps1。
npm.ps1 会被 PowerShell 的默认执行策略直接拦掉（running scripts is disabled）， 于是"装了 npm"被误判成"npm 不可用"，把用户引去重装 Node —— 而问题根本不在那儿。
③ "npm 跑不起来" ≠ "npm 没装"；"端口能通" ≠ "DSH 在跑"。
实测两件事：受限环境里 npm 以 EPERM 失败，但那台机器 npm 装得好好的； 而 8000 端口上是个 C-Lodop 打印服务，它正常返回 HTTP 200， 早先的宽松逻辑把它认成 DSH，于是工具报告"服务运行正常、无需修复" —— 用户以为工具检查过了，其实什么都没查。
⇒ 判据一律收紧：只有拿到强证据（响应里确实有 DSH 标识）才敢说"这是 DSH"。 假阳性比查不出来危险得多，因为它会让用户放心。

七、为什么它"通用"

没有任何一处写死 —— 这是它跟"针对某台机器写的一次性脚本"的根本区别。

通常要写死的它怎么现场问出来
用户名 / 家目录读 $HOME / %USERPROFILE%；报告里把路径缩成 ~ 保护隐私
DSH 装在哪六路兜底逐个验证：DSH_HOME → ~/.dsh → profiles/node_modules → 全局 npm root → dsh shim 反推 → npx 缓存
（本机实测：另有两个工具 dsh-doctor/dsh-recovery 因为只走一条路而报了"找不到 DSH 安装"）
默认端口--port → 环境变量 DSH_WEB_URL → 候选列表（3080/9800/7860/…）逐个真连一次
profile 叫什么扫 profiles/，按"里面有 package.json 或 cordis.patch.yml"来认，不认死 web
备份文件叫什么认 *.bak* 前缀，不套固定格式 —— 实测同一台机器上就同时存在两种命名
哪个软件源能用五个候选源现场并发实测，按延迟排序挑最快的
命令存在吗遍历 PATH 找文件，不调 where/which —— 因为"调系统命令"本身就可能失败

八、用户能做的每一个动作

npx dsh-tudian                 探测 + 诊断 + 自动修复
npx dsh-tudian --dry-run       只检测不修复（只读，推荐先跑）
npx dsh-tudian --yes           全程不询问

  --port <端口>     指定端口          --home <路径>    指定 DSH 主目录
  --profile <名字>  指定 profile      --log <路径>     指定日志位置
  --verbose, -v     多说细节          --quiet, -q      只说结果
  --no-color        关彩色            --persist-registry  允许改全局 npm 源

退出码：0 成功/正常/你取消了 · 2 没修好 · 3 工具自身出错 · 130 按了 Ctrl+C

Windows 用户不想碰命令行：直接双击 一键修复.bat。
