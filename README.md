# dsh-tudian · DSH 启动失败修复工具

> **一句话**：你的 DeepSeek Harness 起不来了？跑一条命令，它自己查清楚哪儿坏了，并把能修的都修好。
>
> One command that diagnoses and repairs a DeepSeek Harness that will not start.
>
> 零依赖 · 全中文 · 跨平台（Windows / macOS / Linux）· 跨版本（不写死任何路径和端口）

📖 **完整介绍（中文 / English）→ [`INTRO.md`](INTRO.md)**

---

## 一分钟上手

```sh
npx dsh-tudian
```

就这一条。它会自动完成：**探测 → 诊断 → 修复 → 验证 → 给你一份报告**。

**推荐先跑一次"只看不动"模式**，确认它看懂了你的问题：

```sh
npx dsh-tudian --dry-run
```

干跑模式**不会改动你的任何配置**（唯一写下的是一份日志文件），
你可以反复跑，跑十次也不会有副作用。

Windows 用户如果不想碰命令行：双击项目里的 **`一键修复.bat`** 就行。

## 它到底会动什么（先看这段）

这是最该先看的一段。修工具最重要的品质是"让人敢按下去"。

### 干跑模式（`--dry-run`）

**只读。** 不写配置、不改链接、不启服务。
唯一写下的是一份日志文件（`dsh-tudian-log.txt`），因为你要靠它反馈问题。

### 正常模式

按故障类型，**最多**动这几样：

| 动作 | 说清楚 |
|---|---|
| 备份你的配置文件 | 命名 `cordis.patch.yml.bak-<时间戳>`，跟 DSH 自己产生的备份同一风格 |
| 从备份恢复配置（仅在配置损坏时） | 恢复前会把你**当前的状态**也再备份一份，恢复错了还能回来 |
| 重建插件的 `node_modules` 链接 | 这是**把插件真正修好**（功能保留），不是禁用它 |
| 重新安装缺失的插件 | 需要联网；会用**临时**指定的软件源，不动你的 npm 全局配置 |
| 停用出问题的那**一个**插件 | 用 DSH 原生的 `disabled` 补丁追加在文件末尾，**原内容一个字节都不改** |
| 启动 DSH 服务 | DSH 自己会往 profile 目录写 `cordis.yml`，这是它的正常行为 |
| 换端口启动（仅在端口被占时） | 不会去杀占用端口的那个程序 |

### 它**从不**做的事

- ✗ 不删除你的任何文件、插件目录、会话记录或数据
- ✗ 不修改你的 npm 全局配置（除非你明确加 `--persist-registry`）
- ✗ 不会一上来就"禁用全部插件"（那是最后手段，而且要你点头）
- ✗ 不会杀进程、不会动防火墙、不会改系统设置
- ✗ 不读也不上传你的任何凭据

## 能修哪些故障

| 故障 | 典型现象 | 能自动修吗 | 它怎么做 |
|---|---|---|---|
| **插件加载失败** | 启动就退，报 `ERR_MODULE_NOT_FOUND: Cannot find package 'xxx'` | ✅ | 先尝试**真正修好**（重建链接 → 重新安装），不行才精确停用那一个，最后才安全模式 |
| **配置文件损坏** | 报 `failed to parse patches` | ✅ | 从历史备份恢复（恢复前双重备份） |
| **端口被占用** | 端口有服务但不是 DSH | ✅ | 自动找一个空闲端口启动 |
| **服务未启动** | 端口没监听，配置正常 | ✅ | 直接启动，并等到端口真的就绪 |
| **npm 源异常** | 装包报 `TAR_BAD_ARCHIVE` / 一直超时 | ✅ | 现场挨个测所有候选源，挑能用的；顺带校验缓存 |
| **Node 版本过低** | 起不来，或报语法/API 不支持 | ✗ 只能提示 | 给出升级步骤（本工具自身能在 Node 18 上跑，就是为了还能告诉你这句话） |
| **profile 目录没写权限** | 启动直接 `EPERM` 退出 | ✗ 只能提示 | 给出改权限的具体命令 |
| **找不到 DSH 本体** | — | ✗ 只能提示 | 多路探测都落空时，告诉你用 `--home` 指定 |

> 你的故障不在表里也不怕：跑 `--dry-run` 看看它怎么说；它认不出来的时候**会老实说"不确定"**，而不是硬猜一个原因去乱改。

## 参数

```
npx dsh-tudian                     探测 + 诊断 + 自动修复
npx dsh-tudian --dry-run           只检测不修复（只读，推荐先跑）
npx dsh-tudian --yes               全程不询问，一路自动执行

  --port <端口>        指定端口（不指定则自动探测 3080 / 9800 / 7860 等）
  --home <路径>        指定 DSH 主目录（默认读 $DSH_HOME，再默认 ~/.dsh）
  --profile <名字>     指定 profile（默认优先 web）
  --verbose, -v        多打细节（原始命令、完整输出）
  --quiet, -q          只打结果
  --no-color           关掉彩色（重定向到文件时自动关）
  --log <路径>         指定日志文件位置
  --persist-registry   允许改**全局** npm 源（默认不改）
  --help, -h           帮助
  --version, -V        版本号
```

**退出码**：`0` 成功/本来就正常/你主动取消 · `2` 没能修好 · `3` 工具自身出错 · `130` 你按了 Ctrl+C

## 它凭什么"通用"

因为**没有任何一处是写死的** —— 这是这个工具的设计目标，也是它跟"针对某台机器写的一次性脚本"的根本区别：

| 通常要写死的东西 | 它怎么现场问出来 |
|---|---|
| 用户名 / 家目录 | 读 `$HOME` / `%USERPROFILE%`，报告里还会把路径缩写成 `~` 保护隐私 |
| DSH 装在哪 | 环境变量 `DSH_HOME` → `~/.dsh` → `profiles/node_modules` → 全局 npm root → `which dsh` 反推 → npx 缓存，**六路兜底逐个验证** |
| 默认端口 | `--port` → 环境变量 `DSH_WEB_URL` → 候选列表（3080/9800/7860/…）逐个真连一次 |
| profile 叫什么 | 扫 `profiles/` 目录，按"里有 package.json 或 cordis.patch.yml"来认，不认死 `web` |
| 备份文件叫什么 | 认 `*.bak*` 前缀，不套固定格式（实测同一台机器上就同时存在两种命名） |
| 哪个软件源能用 | 五个候选源**现场并发实测**，按延迟排序挑最快的 |
| 是不是 DSH 在跑 | 必须拿到强证据（响应里有 DSH 标识）才认，**绝不用"端口能通"凑数** |

### 三条来自真实踩坑的设计决定

**① 端口探测用 Node 的 `net` 模块，不用 `netstat` / `Get-NetTCPConnection`。**
实测：DSH 明明在 3080 上跑着，`Get-NetTCPConnection -LocalPort 3080 -State Listen` 却返回**空**，
于是判断成"端口空闲、服务没起来"——**完全反了**。
这类"系统工具被权限限制后静默返回空结果"的坑很阴险：它不报错，只是悄悄少给你东西。
`net.connect()` 不受这类限制，且跨平台行为一致。

**② Windows 上永远走 `npm.cmd`，绝不碰 `npm.ps1`。**
`npm.ps1` 会被 PowerShell 的默认执行策略直接拦掉（`running scripts is disabled`），
于是"装了 npm"会被误判成"npm 不可用"，把用户引去重装 Node。

**③ "npm 跑不起来" ≠ "npm 没装"。**
实测在受限环境里 npm 以 `EPERM` 失败，但那台机器 npm 装得好好的。
所以判据拆成"命令存不存在"和"跑不跑得起来"两条 ——
而且**只有前者为假才算没装**；后者只是"联网装包这条路不通"，
恢复备份、重建链接、启动服务照样能修。
除此之外，本工具本身只要 Node ≥ 18 就能跑（DSH 要 ≥ 22.19.0），
图的就是在"你 Node 太老"这种情况下，它还能跑起来把这句话告诉你。

## 常见问题

**Q：跑完还是起不来怎么办？**
报告最后一段就是给你的手动步骤，一条条照做。还不行就把 `dsh-tudian-log.txt` 发出来 ——
里面记录了每一步的原始命令和输出，不用你复述。

**Q：会不会把我的插件都禁掉？**
不会。顺序是刻意排的：① 重建链接真正修好 → ② 重新安装 → ③ **只**停用出问题的那一个 →
④ 安全模式（全部停用）。第 ④ 步**默认不会执行**，要你明确点头，而且随时能撤销：
`npx dsh-fix clear`。

**Q：它改了我的 npm 源怎么办？**
默认**不改**。只在装包时给那一条命令临时带上 `--registry`。
只有你显式加了 `--persist-registry` 才会写全局配置，而且报告里会告诉你原值是什么、怎么改回去。

**Q：备份文件太多怎么办？**
重复跑不会堆备份：备份前会算内容指纹，**内容完全相同就复用**。
确认一切正常后，备份可以自己删（`*.bak-*` 这些文件）。

**Q：`dsh-fix` 和这个工具是什么关系？**
`dsh-fix` 是另一个独立的 DSH 修复工具，很优秀，专门做"停用插件 / 两分法定位"。
`dsh-tudian` 在需要时会**调用它**（先看有没有装，没有则装），
但 `dsh-tudian` 自己多做两件事：**环境探测**和**真正把插件修好**（而不只是停用它）。
两者配合，不是替代。

**Q：为什么端口探测要连好几个端口？会不会打扰我别的服务？**
只对每个候选端口发**一个** HTTP `GET /`，读完响应头就断开，不会改动对方任何状态。
读不到 DSH 标识就判定"这不是 DSH"，不会误认。

**Q：我 DSH 装在特别的位置，探测不到？**
`npx dsh-tudian --home "D:\你的路径\.dsh"` 直接告诉它。

## 日志

每次运行都会在当前目录生成 **`dsh-tudian-log.txt`**，包含：

- 完整的环境探测结果
- 执行的每一条命令 + 它的原始输出 + 退出码
- 每一步的判断依据
- 所有改动过的文件及其备份路径

**反馈问题时只需要发这一份文件**，不需要你回忆或复述任何东西。

> 日志里不会出现凭据（内置了打码过滤）。路径会带你的用户名，
> 介意的话发之前自己搜一下替换掉。

## 项目结构

```
dsh-tudian/
├── bin/dsh-tudian.mjs          命令行入口（参数解析 + 帮助）
├── lib/
│   ├── exec.mjs            跨平台命令执行（三个平台坑都在这）
│   ├── log.mjs             日志（带时间戳，失败自动降级）
│   ├── ui.mjs              终端输出与交互（中文、进度、确认）
│   ├── util.mjs            纯工具函数（版本比较、链接识别、路径缩写）
│   ├── net.mjs             端口与 HTTP 探测（只用 net 模块）
│   ├── registry.mjs        软件源探测与切换（温和档优先）
│   ├── probe.mjs           环境探测层 ★全部只读
│   ├── diagnose.mjs        故障诊断层（纯判断）
│   ├── repair.mjs          修复层 ★唯一会动盘的地方
│   ├── flow.mjs            主编排（把上面串成一条线）
│   └── report.mjs          报告输出
├── 一键修复.bat            Windows 双击入口（UTF-8 BOM 编码）
├── open.vbs                双击看架构图（纯 ASCII）
└── design.html             架构设计图（浏览器里看）
```

**分层是有意为之**：探测层只读 → 诊断层只判断 → 修复层才写盘。
所以 `--dry-run` 的安全性是一眼可查的 —— 想验证它有没有偷偷写东西，
grep 一下 `lib/repair.mjs` 就够了。

---

**Q：为什么 `一键修复.bat` 里面全是英文？**
因为 **cmd.exe 解析含中文的 bat 文件有缺陷** —— 它会把行拆错位置，
然后把中文句子的后半截当成命令去执行，报一串
`'...' is not recognized as an internal or external command`（实测踩过）。
所以 bat 保持**纯 ASCII**，中文提示全部交给 Node 程序输出
（靠开头的 `chcp 65001` 保证中文在控制台里显示正常）。
同理，`open.vbs` 也必须纯 ASCII —— 那是另一个实测坑：VBS 里写中文会直接弹「无效字符 800A0408」。

**Q：为什么装了 `dsh-tudian` 还要装 `dsh-fix`？**
不用你先装 —— 工具会先看你的机器上有没有，没有才装。
而且装的时候用的是**临时指定的源**，不会改你的 npm 全局配置。

### 测试

`_tools/` 里有两个测试套件，共 **64 项**，全部只碰自己的沙盒目录，**不碰任何真实 DSH 文件**：

| 测试 | 项数 | 测什么 | 为什么值得单独测 |
|---|---|---|---|
| `_tools/test-backup.mjs` | 18 | 备份 / 恢复 / 幂等 / 干跑不写盘 | 备份是整套安全承诺的**地基**，它不灵、整套都不灵 |
| `_tools/test-diagnose.mjs` | 46 | 配置损坏判定 + 启动日志解析 + 全部分支判定 | 前者的**假阳性代价极大**（会拿备份覆盖一份好配置），所以 15 个用例全是"正常文件绝不能误报" |

> 第二套里有一组是**纯逻辑分支测试**：直接喂构造出来的探测结果给诊断函数。
> 因为有些分支在真机上根本走不到 —— 比如"端口冲突"要求"没有任何 DSH 在跑"，
> 而开发这台机器上 DSH 正开着，总不能为了让测试跑通就把用户的服务停掉。

`_tools/fake-home/` 和 `_tools/fake-home2/` 是两个**模拟故障环境**（插件没装 / 配置损坏），
用来演练各条诊断分支而不动真实 DSH：

```sh
node bin/dsh-tudian.mjs --dry-run --home _tools/fake-home     # 演练"插件加载失败"
node bin/dsh-tudian.mjs --dry-run --home _tools/fake-home2    # 演练"配置文件损坏"
node bin/dsh-tudian.mjs --dry-run --port 8000                 # 演练"端口被别的程序占"
```
